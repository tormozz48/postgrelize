# ADR-034: Constructable CommonJS entry and default export

**Status:** Accepted
**Date:** 2026-11-22
**Feature:** Sequelize v6 parity (package entry)
**Author:** 10x-Team (Principal Architect)

## Context
Running Sequelize v6's own tests against postgrelize (`.10x/specs/2026-11-22-v6-compat-gate-design.md`, gate 1) showed two differences in the package entry that no scenario in `tests/compat` covers:

1. `require('sequelize')` is the `Sequelize` class in v6 (`lib/index.js` is `module.exports = require('./sequelize')`, which does `module.exports = Sequelize` and adds `Sequelize.Sequelize`, `Sequelize.default` and every helper as statics). `require('postgrelize')` is a namespace object, so the usual v6 line `const Sequelize = require('sequelize'); new Sequelize(url)` throws `is not a constructor`. `docs/guide/migrating.md` says `require('postgrelize')` works; it works only as `require('postgrelize').Sequelize`.
2. v6's `lib/index.mjs` has `export default Pkg` (the class) next to the named exports, so `import Sequelize from 'sequelize'` is the documented form in v6's own docs. `import Sequelize from 'postgrelize'` fails with `does not provide an export named 'default'`. `tests/compat/api-surface-exceptions.json` lists `default` as "v6 internal", which hides the impact.

Plain-JavaScript and default-import code is common in v6 applications, and these are the first lines of the migration. The `exports` map (`import` to `dist/index.js`, `require` to `dist/index.cjs`, both built by Vite from `src/index.ts`) stays as it is.

## Decision
- **ESM:** `src/index.ts` adds `export { Sequelize as default }`. The named exports are unchanged. `import Sequelize from 'postgrelize'` and `import { Sequelize } from 'postgrelize'` both work and are the same class. The declarations get the same default export.
- **CommonJS:** `dist/index.cjs` exports the `Sequelize` class itself, with every named export copied onto it as a static property, `Sequelize.Sequelize` and `Sequelize.default` pointing to the class, like v6. `require('postgrelize')` is constructable; `require('postgrelize').Sequelize`, `.DataTypes`, `.Op`, ... keep working, so existing consumers do not break. The Vite build still emits the namespace bundle (as `dist/index.cjs`'s private input, `dist/index.core.cjs`) and a small build step writes the `index.cjs` wrapper; copied names never replace a static that the class already defines, and the copies are plain data properties (no getters).
- No `export =` in the declarations: it would break `import { Sequelize }` under ESM resolution. TypeScript consumers use the default export, which exists in the ESM and CJS builds (`exports.default`).
- `tests/build/package-entry.test.ts` and `tests/build/declarations.test.ts` assert both forms in both module systems and in a strict consumer. The `default` entries leave `api-surface-exceptions.json`. `docs/guide/migrating.md` shows the three import forms.
- Release: minor version. The change is additive: `require('postgrelize')` changes from an object to a function that carries the same properties, and a `default` export appears; nothing a previous consumer could rely on is removed. Code that tested `typeof require('postgrelize') === 'object'` is the only break and is not a supported use.

## Alternatives Considered
| Alternative | Pros | Cons | Why Not |
|---|---|---|---|
| Document `require('postgrelize').Sequelize` and `import { Sequelize }` only | No code | Every plain-JS v6 file and every `import Sequelize from` line fails on migration; v6's own docs use both | The goal is a drop-in replacement; the cost is a few lines |
| `export =` / `module.exports = Sequelize` as the only CJS shape, generated by the bundler | Simple | TypeScript `export =` cannot be combined with named exports in the same declaration file; `import { Sequelize }` breaks for ESM resolution | Breaks the primary import form |
| Wrapper function or Proxy around the class as the CJS export | Keeps the namespace object untouched | `instanceof`, static inheritance (`class X extends Sequelize`) and `new.target` behave differently from v6 | The class itself must be the export |
| Add `default` to ESM only | Smaller change | CJS users of v6 code stay broken | Half of the gap |
| Define getters for the copied statics | Live bindings | Different from v6 (plain properties) and slower on hot paths such as `Op` | Not needed: the exports are constants |

## Consequences
### Positive
- `require('postgrelize')` and `import Sequelize from 'postgrelize'` work as in v6; the migration guide can say "change the package name".
- The differential gate can run v6 code that imports through either form.
### Negative
- A post-build step and a second CJS file; `tests/build` must keep passing on Node 20, 22 and 24.
- The `Sequelize` class carries about 150 extra static properties in CJS, as in v6. Names already used by the class win; a clash is a build-time test failure, not a silent overwrite.
- Bundlers that statically analyse `require` see a function export; tree-shaking of the CJS build is not a goal.
### Risks
- Two default-import conventions exist for CJS consumers compiled with `esModuleInterop`. Both `Sequelize` and `Sequelize.default` resolve to the class, so they agree.
- A future named export that collides with a `Sequelize` static needs a decision at that time; the build test names the clash.
